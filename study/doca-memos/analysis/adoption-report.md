# BlueField를 NIXL 백엔드로 붙이기 위한 조건 — 기존 스토리지 백엔드와의 차별점

> **작성 목적**: CMX 체계에서 NIXL을 통해 BlueField를 NVMe KV Command Set으로 가동할 때,
> 기존 NIXL 스토리지 백엔드(로컬 SSD, S3, Azure Blob 등)와 무엇이 다른가.
>
> **근거**: PR #1717 코드 전체, NIXL 코어 및 타 백엔드 12종 대조, PR의 목·테스트 레이어,
> nixlbench 통합분, GTC 2026 S81773 발표 전문, NVMe KV Command Set 사양.
> **작성 시점 기준 PR 상태: open(미머지), DOCA 4.4 미공개 → 빌드·실행 불가.**

---

## 요약

**차별점은 세 층에서 발생한다.**

| 층 | 차별점의 성격 |
|---|---|
| **프로토콜** | 블록/오브젝트가 아니라 **NVMe KV Command Set**. key 16바이트 상한, value 크기가 볼륨에 고정 |
| **데이터 경로** | **GPU 직행 불가.** 반드시 host DDR 경유 — 같은 OBJ_SEG 백엔드 중 유일 |
| **운영 모델** | **내구성 100%를 포기**한 설계. retrieve 실패가 정상 케이스이며, 이를 프레임워크가 처리해야 함 |
| **진행 모델** | 무스레드 모드에서는 **호출자의 폴링이 진행의 조건**이다. 스토리지 백엔드 중 POSIX 만 같은 방식이며, **설정에 따라 방식이 바뀌는 것은 이 백엔드뿐** |

**결론**: 플러그인 자체는 얇다(실질 6개 함수). **도입 난이도는 플러그인이 아니라 그 위(추론 프레임워크 수정)와 아래(DPU·볼륨 구성)에 있다.**

**가장 실질적인 제약 하나**: 전송 하나에 상태 하나뿐이라 **배치 안에서 어느 KV 블록이
miss 였는지 알 수 없다.** 발표가 요구한 context hole 계산(빠진 것만 재계산)이
현재 코드로는 성립하지 않으며, **블록당 요청을 나누거나 NIXL 코어 API 를 확장해야 한다** (2.6-1).

## 1. 선행 조건 — 코드가 돌기 전에 갖춰져야 하는 것

플러그인은 아래 상태를 **전제**한다. 만들지도, 탐색하지도 않는다.

```
① BlueField-4 가 NVMe KV 컨트롤러를 하드웨어 에뮬레이션하도록 구성
       ↓ PCIe 열거
② 리눅스 표준 NVMe 드라이버가 바인딩 → /dev/nvmeXnY 존재
③ CMX 박스에 모델별 KV 볼륨 생성 (제어 평면)
④ 호스트에 DOCA 4.4 이상 설치 (libdoca_kv, libdoca_common)
────────────────── 여기까지 되어야 ──────────────────
⑤ agent.createBackend("DOCA_MEMOS", {device_name, nguid, ...})
```

**①③④는 이 PR 바깥이며 전부 비공개 영역 또는 하드웨어다.** PR이 담당하는 것은 ⑤ 이후뿐이다.

## 2. 기존 백엔드와의 차별점

### 2.1 GPU 메모리 직행이 불가능하다 — **가장 큰 실무적 차이**

| 백엔드 | 지원 memory type | GPU 직행 |
|---|---|---|
| GDS / GDS_MT | `{DRAM, VRAM, FILE}` | ✅ |
| **OBJ (S3) — Dell 가속 엔진** | `{OBJ, DRAM, VRAM}` | ✅ |
| OBJ (기본 S3) | `{OBJ, DRAM}` | ❌ |
| **DOCA_MEMOS** | **`{OBJ, DRAM}`** | **❌** |

전송 준비 단계에서 local 쪽이 `DRAM_SEG`가 아니면 명시적으로 거부한다.

**왜 그런가 — 근거 불명.** 다만 **NIXL의 제약이 아님은 확실하다.** OBJ 백엔드 프레임워크가
GPU 직행을 명시적으로 예상하고 있다:

> *"Vendor engines that support GPU-direct transfers should override this to include VRAM_SEG."*
> — `src/plugins/obj/s3_accel/engine_impl.h`

같은 `OBJ_SEG` 계열에서 Dell 벤더 엔진이 실제로 구현했다. 즉 **DOCA_MEMOS의 DRAM 전용은 플러그인의 선택**이다.

가능한 근거 후보:
- 초기 릴리스에서 의도적으로 범위를 좁힘
- `doca_kvdev` API의 iovec이 GPU 메모리 주소를 아직 받지 못함
- NVMe KV passthrough 경로에서 GPUDirect Storage가 성립하지 않음

**실무적 함의**: CMX↔GPU 사이에 **host DDR 복사 1회가 추가**된다. 그 복사는 NIXL 밖(프레임워크 몫)이며,
GTC 발표의 huge page 요구가 여기서 나온다.

### 2.2 등록(registerMem)이 장치를 전혀 건드리지 않는다

| 백엔드 | 등록 시 하는 일 |
|---|---|
| UCX | 페이지 고정(pin) + NIC 등록 + rkey 생성 — **비쌈** |
| POSIX (path-mode) | devId 유일성 예약, 경로 파싱 |
| Azure Blob | devId→blob 이름 매핑 테이블 유지 |
| **DOCA_MEMOS** | **문자열 → 16바이트 key 변환. DOCA 호출 0회** |

**왜 그런가 — 근거 확실.** KV 캐시는 프리픽스 해시가 계속 새로 생기므로 **등록이 워크로드 내내
반복**된다. 여기서 장치 왕복이 발생하면 성능이 무너진다.

GTC 발표의 요구사항과 정확히 대응한다:

> *"당신의 추론 시스템에서 KV 캐시 메타데이터를 모으지 마라. CMX 박스는 사실상 무한(18PB)이다.
> 거기 저장하는 KV마다 메타데이터를 유지하면 DRAM을 전부 잡아먹는다. DOCA MEMOS가 알아서 한다."*

**실무적 함의**: 등록이 값싸므로 프레임워크가 key마다 자유롭게 등록/해제해도 된다.
반면 **NIXL의 등록/전송 분리 모델이 이 백엔드에는 이득이 거의 없다** — 재사용할 비싼 준비물이 없기 때문.

### 2.3 key가 16바이트 고정 상한

| 백엔드 | key/식별자 형태 |
|---|---|
| POSIX / GDS | 파일 경로 또는 fd — 사실상 무제한 |
| OBJ (S3) / Azure Blob | 오브젝트 이름 문자열 — 수백 바이트 |
| **DOCA_MEMOS** | **정확히 16바이트 이하** |

**왜 그런가 — 근거 확실.** NVMe KV Command Set의 최대 key 길이가 16바이트이고,
발표의 *"128-bit keys at the moment"* 와 정확히 일치한다.

런타임에 장치가 16보다 큰 값을 보고하면 **초기화 자체를 실패**시킨다(잘라 쓰지 않는다).

**실무적 함의**: **프레임워크의 프리픽스 해시가 128비트 이하여야 한다.** 상류 제약이다.

### 2.4 value 크기가 볼륨에 의해 고정된다

초기화 시 장치에서 최대 value 길이를 읽어 보관하고, 제출 시 버퍼가 그보다 크면 거부한다.
별도로 `UINT32_MAX` 상한도 검사한다.

**왜 그런가 — 근거 확실.** KV 볼륨은 **특정 max KV 블록 크기로 사전 구성**된다.
설계 철학의 첫 번째 단순화가 이것이다:

> KV 캐시는 크기가 고정 → 스토리지를 그 granularity로 사전 구성 → **write amplification ≈ 1**

**실무적 함의**: **모델과 볼륨이 짝지어져야 한다.** DeepSeek용 1MB 볼륨에 Llama의 10MB 블록을
넣으면 실패한다. 용량 부족이 아니라 **규격 불일치**다.

> **관찰된 과도한 제약**: 이 검사는 READ/WRITE를 구분하지 않고 적용된다.
> READ에서 버퍼를 넉넉히 잡아도 거부된다. WRITE 기준으로는 타당하나 READ에는 불필요해 보인다.

### 2.5 존재 조회가 기본적으로 장치에 도달하지 않는다

`queryMem()` 은 **NIXL의 기존 SB API**다 (이 PR이 만든 것이 아니며, 기본 구현은
`NIXL_ERR_NOT_SUPPORTED`). 이 플러그인은 그것을 구현하되 두 모드를 둔다.

| `query_mem_mode` | 동작 |
|---|---|
| `assume_success` (기본) | **장치에 묻지 않고** 모든 descriptor 에 "있음" 을 반환. I/O 없음 |
| `actual` | NVMe KV **EXIST 명령**을 발행해 실제로 확인 |

> 용어: `queryMem` 은 NIXL API, EXIST 는 NVMe KV 장치 명령이다.
> EXIST 는 `actual` 모드가 그 질문에 답하기 위해 쓰는 수단일 뿐 NIXL 명령이 아니다.

**왜 그런가 — 근거는 정황.** GTC 발표에 대응하는 요구가 있다:

> *"retrieve 전에 exist를 하지 마라. retrieve 자체가 exist 검사이고, exist가 yes여도
> retrieve 시점엔 사라졌을 수 있다. 네트워크 왕복만 낭비다."*

다만 코드에 이 근거가 적혀 있지는 않다. 확실한 것은 **응답 형식이 "있음 / 없음" 둘뿐이라
"모름" 을 표현할 자리가 없다**는 점이다. 둘 중 하나를 골라야 하고,
**"있음" 이라야 프레임워크가 retrieve 까지 진행한다.** 그 지점에서 진짜 답이 나온다.

정확히는 *"exist 를 쓰지 마라"* 가 아니라 **"물어봐도 정보를 주지 않는다"** 이다.
비용은 거의 없고(I/O 없음) 대신 답에 정보가 없다.

**부수 발견 — EXIST 는 항상 에러 콜백으로 온다.** `ALREADY_EXIST` = 있음,
`NOT_FOUND` = 없음. 다른 DOCA 태스크와 규약이 반대다.

이것은 DOCA 의 기벽이 아니라 **NVMe KV 규격이 비쳐 보이는 것으로 보인다** — NVMe KV 는
키 존재 여부를 **상태 코드로** 보고하고, DOCA 는 상태값이 0이 아니면 에러 콜백으로 보낸다.
*(스펙 대조 필요)*

**`actual` 모드의 성질 — 동기 블로킹, 타임아웃 없음.** `waitForQueryCompletion()` 이
모든 콜백이 돌아올 때까지 반환하지 않는다. 질의 핸들이 그 함수의 지역 변수이므로
**타임아웃을 넣으면 use-after-free 가 된다** — 저자가 주석으로 명시했다.
즉 **장치가 응답하지 않으면 호출한 스레드가 무한 대기**한다.

**실무적 함의**: 기본 설정에서 `queryMem` 의 결과로 판단하면 안 된다.
벤치마킹 시 기본값이 비용을 숨기므로 QUERY 측정에는 `actual` 을 명시해야 하며,
`actual` 을 운영에 쓸 경우 무한 대기 가능성을 감안해야 한다.

### 2.6 retrieve 실패가 정상 케이스다

이 프로젝트의 정체성인 **"내구성 100% 보장 포기"** 가 코드에 나타나는 지점.
KV 캐시는 재계산 가능하므로 99.8% hit rate 면 충분하다는 판단이다.

**기본 동작(`ignore_read_not_found=false`)에서 miss 는 전송 실패로 보고된다.**
프레임워크는 실패를 받고 재계산하면 된다 — 발표의 *"retrieve 실패를 정상 케이스로 처리하라"* 와
정합한다. 왕복은 생략하되(2.5) miss 는 알려주는 조합이다.

**`ignore_read_not_found=true` 는 그 보고마저 없앤다.** 없는 key 에 대한 retrieve 가
**성공으로 반환**되고 버퍼 내용은 undefined 다. 이전 내용이 그대로 남은 채 성공이 온다.

> 이 옵션은 내구성 포기를 *감당하는* 장치가 아니라, **miss 처리 비용을 측정에서 빼기 위한
> 벤치마크 성격**으로 읽힌다. 켜면 프레임워크가 miss 를 감지할 경로가 사라져
> 발표의 요구(재계산, context hole)를 오히려 수행할 수 없게 된다.
> **운영 도입 시 켜지 않는 것을 전제로 검토해야 한다.**

**실무적 함의 — 가장 큰 상류 작업**: 프레임워크가 아래 둘을 처리해야 한다.

1. **retrieve 실패를 정상 흐름으로** 취급
2. **context hole 계산** — 중간 블록 하나가 없다고 그 뒤 전부 버리지 말고 빠진 것만 재계산

발표는 vLLM과 Dynamo에서 이 작업이 진행 중이라고 밝혔다. **즉 CMX 도입은 드라이버 설치가 아니라
추론 프레임워크 수정을 수반한다.**

다만 2번은 현재 코드로 수행할 수 없다. 아래 2.6-1 참조.

### 2.6-1 어느 descriptor 가 miss 였는지 알 수 없다 — **context hole 계산의 전제가 무너진다**

기본 설정에서도 남는 문제이며, 이번 조사에서 확인된 가장 실질적인 제약이다.

전송 하나에 상태 하나뿐이다. `checkXfer()` 도 `getXferStatus()` 도 `nixl_status_t` 를
하나만 돌려주며, **descriptor 별 결과를 담을 자리가 NIXL API 에 없다.**

```
descriptor 100개를 한 번에 retrieve
    그중 37번 key 가 없음
        → 에러 콜백이 overallStatus_ 에 NIXL_ERR_BACKEND 기록
        → fail-fast: 나머지 제출 중단
    checkXfer → NIXL_ERR_BACKEND 하나
```

프레임워크가 아는 것은 **"이 전송이 실패했다"** 뿐이다. 어느 블록이 없었는지,
심지어 **miss 때문인지 장치 고장 때문인지도** 구별되지 않는다.

**왜 그런가 — 근거 확실.** NIXL 에 per-task 상태 보고 API 가 없다는 사실이
fail-fast 배치 처리의 이유였는데(5장⑤), 여기서 두 번째 대가를 치른다.

**보완 가능한 위치 — 비용 순**

| 위치 | 방법 | 비용 |
|---|---|---|
| **플러그인** | miss 에 `NIXL_ERR_NOT_FOUND` 를 쓴다 (아래) | 거의 없음. 단 어느 descriptor 인지는 여전히 모름 |
| **프레임워크** | KV 블록 하나당 전송 요청 하나 | 요청 수가 블록 수만큼 증가 |
| **NIXL 코어** | descriptor 별 상태 반환 API 추가 | API 변경. 전 백엔드 영향 |

**관찰 — 기존 상태 코드를 쓰지 않는다.** NIXL 에 `NIXL_ERR_NOT_FOUND`(-4) 가 이미 있는데,
플러그인은 **키 부재와 장치 오류를 모두 `NIXL_ERR_BACKEND`(-3)** 로 보고한다.
API 변경 없이 두 원인을 갈라낼 수 있는데 하지 않고 있다.

**실무적 함의**: 현 상태로는 **부분 재계산이 불가능하고 배치 전체를 재계산해야 한다.**
블록당 요청 하나로 쪼개면 가능하지만 요청 수가 늘어난다.
**도입 설계 단계에서 결정해야 할 항목이다.**

### 2.7 오브젝트 스토리지 헬퍼가 없다

`OBJ_SEG`를 쓰지만 S3/Azure 계열의 CRUD 헬퍼(putObj/getObj/rmObj)가 없다.
nixlbench가 이를 위해 판정 함수를 **새로 분리**했다 — `isObjStorageBackend()`에는 포함하되
`hasObjectStorageHelpers()`에서는 제외.

결과로 `--check_consistency` 옵션이 명시적으로 거부된다:

> *"일반 정합성 검사는 S3/Azure 오브젝트 헬퍼로 쓴 데이터를 되읽는데, DOCA_MEMOS는 그것을 구현하지 않는다."*

**왜 그런가 — 근거 확실.** KV 장치는 오브젝트 스토리지가 아니다. 플러그인은 Delete/List를 쓰지 않고
STORE/RETRIEVE/EXIST 셋만 사용한다.

**실무적 함의**: 같은 `OBJ_SEG`라도 **기존 오브젝트 스토리지 운영 도구·테스트 경로를 재사용할 수 없다.**

### 2.8 notification 미지원

스토리지 백엔드 공통 특성이나 명시해 둔다. 전송이 전부 자기 자신으로의 loopback이므로
알릴 상대가 없다. 완료 확인은 폴링(`checkXfer`)으로만 이루어진다.

### 2.9 agent 하나당 백엔드 인스턴스 1개

NIXL 코어가 같은 타입의 백엔드 중복 생성을 거부한다.

**실무적 함의**: **NVMe KV 장치를 두 대 붙이려면 agent를 두 개 만들어야 한다.**
한 노드가 두 모델을 돌리며 두 볼륨을 쓰는 시나리오(발표에서 언급됨)에서 걸릴 수 있는 제약이다.

### 2.9-1 value 버퍼가 **물리적으로 연속**이어야 한다 — SGL 미사용

DOCA task에 버퍼를 설정하는 API는 iovec **배열과 개수**를 받는다:

```
..._set_key_value_conf(task, key, key_len, struct iovec *value_iovecs, uint32_t iovcnt, value_len)
                                                                       ↑ 개수를 받는다
```

**API는 scatter-gather를 지원한다.** 그런데 플러그인은 store/retrieve 두 곳 모두에서
`iovcnt` 자리에 **`1`을 하드코딩**한다. 즉 value 하나가 iovec 하나 = 연속 버퍼 하나여야 한다.

| 백엔드 | SGL |
|---|---|
| UCX | `NIXL_UCX_SGL_ENABLE` 로 켜는 SGL put 경로 보유 (`ucx_sgl.h`) |
| **DOCA_MEMOS** | **미사용. 항상 iovec 1개** |

**왜 그런가 — 근거 불명.** API가 개수를 받는 이상 플러그인의 선택이다.

가능한 근거 후보:
- 초기 릴리스의 범위 축소 (SGL은 후속 과제)
- KV 볼륨이 고정 크기 슬롯 구조라 값이 애초에 연속으로 다뤄짐
- 장치측이 실제로는 iovcnt=1만 처리 (목이 `value_iovecs[0]`만 읽는 것이 정황이나,
  목의 단순화인지 실제 제약의 반영인지 구분 불가)

**실무적 함의**: 프레임워크가 **KV 블록 하나를 연속된 host DDR 영역에 담아야** 한다.
블록이 여러 조각으로 흩어져 있으면 미리 모아야 하며, 이는 huge page 요구와 같은 방향의 압력이다.

### 2.9-2 스토리지 백엔드 중 유일하게 progress 모드를 이중 구현한다

`enableProgTh` 값에 따라 **별도 클래스 두 개**(스레드형 / 무스레드형)를 갈라 만드는 백엔드는
`ucx`, `libfabric`, `doca_memos` 셋뿐이다. 앞의 둘은 네트워크 백엔드다.

| 백엔드 | 스레드 사용 | `enableProgTh` 분기 |
|---|---|---|
| OBJ / GDS_MT / HF3FS / Azure Blob | 있음 | **없음** |
| UCX / LibFabric (네트워크) | 있음 | 있음 |
| **DOCA_MEMOS (스토리지)** | 있음 | **있음** |

다른 스토리지 백엔드는 스레드를 쓰더라도 agent의 설정을 참조하지 않고 자체 정책으로 돈다.

**왜 그런가 — 근거 부분적.** 플러그인 README가 밝힌 의도는 "호출자가 전용 스레드를 감당할 수
있으면 threaded 모드가 경합이 적다"는 것이다. 다만 **스토리지 백엔드에 네트워크급 동시성 설계를
적용한 이유**는 명시돼 있지 않다.

가능한 근거 후보:
- KV 캐시 워크로드의 IOPS가 파일/오브젝트 스토리지보다 훨씬 높을 것을 상정
- 저자(SPDK 창시자 중 한 명)의 설계 습관
- 커스텀 이벤트 루프를 쓰는 추론 런타임에 얹힐 것을 대비

**실무적 함의**: 이 선택이 **1,039줄짜리 progress engine의 주된 복잡도 원인**이다.
더블버퍼 producer 큐, 원자적 완료 게시, 취소 지연 삭제가 전부 여기서 나온다.
도입 시 agent 생성 설정(`enable_prog_thread`)이 백엔드 내부 구조를 통째로 바꾼다는 점을
운영에서 인지해야 한다.

#### 그 선택이 바꾸는 것 — 폴링이 의무가 되는가

두 모드의 차이는 내부 구조에 그치지 않고 **호출자의 의무를 바꾼다.**

무스레드형에서 `checkXfer()` 는 상태를 읽기 전에 **엔진을 한 바퀴 돌린다** —
완료를 거두고(콜백 실행), 밀린 요청을 재시도한 뒤에야 답한다.
**부르지 않으면 전송이 진행되지 않을 뿐 아니라, 완료된 task 가 반납되지 않아
task pool 이 말라 백엔드 전체가 멈춘다.**

타 백엔드와 대조하면 이 방식이 소수도 다수도 아니다.

| 백엔드 | `checkXfer` 가 하는 일 | 진행을 구동하나 |
|---|---|---|
| POSIX | `io_queue_->poll()` | **✅** |
| **DOCA_MEMOS (무스레드)** | `doca_pe_progress` + 재시도 | **✅** |
| DOCA_MEMOS (스레드) | 베이스 — 완료 플래그만 읽음 | ❌ |
| GDS_MT | `future.wait_for(0)` | ❌ 스레드풀이 한다 |
| OBJ (S3) | `getOverallStatus()` | ❌ SDK 스레드가 한다 |
| HF3FS | 카운터 비교 | ❌ 전용 io 스레드가 한다 |

NIXL API 자체는 어느 백엔드든 폴링 모델이다. 차이는 **"안 물어보면 멈추느냐"** 하나뿐이고,
거기서 POSIX 와 DOCA_MEMOS 무스레드형이 같은 편에 선다.

**차별점은 DOCA_MEMOS 만 그 선택이 배포 설정에 달려 있다는 점이다.** 다른 백엔드는 방식이
코드에 고정돼 있다. **같은 백엔드가 설정에 따라 두 진영을 오간다.**

#### 부수 효과 — 에러를 보는 시점이 모드마다 다르다

무스레드형 `postXfer()` 는 제출 도중 복구 불가 에러가 나면 **확정된 실패를 즉시 반환**한다.
스레드형은 제출을 나중에 하므로 **항상 `NIXL_IN_PROG`** 를 반환하고, 실패는 `checkXfer()` 로만
드러난다. **같은 프레임워크 코드가 설정에 따라 다른 시점에 에러를 본다** —
에러 처리 경로는 두 모드 모두에서 시험해야 한다.

#### `pthrDelay` 기본값이 0 — busy-spin

`nixl_params.h:36` 의 `kDefaultPthrDelayUs = 0`. **progress thread 를 켜고 딜레이를 명시하지
않으면 스레드가 자지 않고 `doca_pe_progress` 를 최대 속도로 돌려 CPU 코어 하나를 소모한다.**
`createProgressEngine()` 이 경고를 찍지만 거부하지는 않는다.

GPU 노드에서 추론 프레임워크와 CPU 를 나눠 쓰는 상황이므로 무시할 수 없다.
**스레드 모드를 쓸 거면 `pthrDelay` 를 반드시 함께 지정해야 한다.**

| 딜레이 | CPU | 완료를 거두기까지 |
|---|---|---|
| 0 | **코어 1개** | 최소 |
| 10us | 낮음 | 최대 10us |
| 1000us | 거의 없음 | 최대 1ms |

이 값은 **바쁠 때는 폴링 간격, 한가할 때는 최대 대기 시간**으로 두 역할을 겸한다.
완료가 생겨도 다음 폴링까지 거둬지지 않으며 **그동안 task 도 반납되지 않는다.**

#### 스레드형은 전송마다 descriptor 목록을 복사한다

무스레드형은 task pool 부족으로 밀렸을 때만 복사하지만, 스레드형은 실제 제출이 나중에
다른 스레드에서 일어나므로 **전송 한 건마다 local/remote 목록 두 개를 힙에 복사**한다.
descriptor 가 많으면 무시하기 어렵다.

### 2.9-3 `estimateXferCost` 미구현 — 영향 범위는 제한적

전체 백엔드 중 이 함수를 구현한 것은 `ucx`, `libfabric` 둘뿐이다. 기본 구현은
`NIXL_ERR_NOT_SUPPORTED`를 반환한다.

**중요 — 백엔드 선택에는 영향이 없다.** 코어의 백엔드 선택 로직은 memory type과 등록 범위만 보며,
비용을 참조하지 않는다(*"현재는 순회하며 첫 번째 로컬 매치를 찾는다. 선호 목록이나 더 철저한
탐색을 쓸 수 있다"* 는 주석이 코어에 남아 있다). `estimateXferCost`는 **이미 만들어진 요청 핸들에
대해** 사용자가 호출하는 조회 API다.

**실무적 함의**: 스케줄링 품질에는 영향이 없고, **사용자가 "이 전송이 얼마나 걸릴지" 미리 물을 수
없을 뿐**이다. 다만 CMX는 지연 특성이 로컬 SSD와 크게 다르므로, 상위 스케줄러가 비용 추정을
활용하려는 경우 이 백엔드만 답을 주지 못한다.

### 2.10 장치 자동 탐색이 없다

플러그인은 사용자가 지정한 경로 하나를 열 뿐이며, 어느 장치가 CMX 백엔드인지 판별하지 못한다.

**실무적 함의**: 노드에 NVMe가 여럿이면 **배포 주체가 어느 노드 파일이 CMX인지 알아야 한다.**
게다가 `/dev/nvmeXnY` 이름은 재부팅 시 바뀔 수 있다. `nguid` 파라미터가 이 문제의 완화책일
가능성이 있으나 확인되지 않았다(4장 참조).

## 3. 만족시켜야 하는 값과 제약 — 점검표

### 3.1 설정 파라미터

| 이름 | 필수 | 기본값 | 제약 |
|---|---|---|---|
| `device_name` | **예** | — | NVMe KV 장치 경로. 없으면 백엔드 생성 실패 |
| `num_tasks` | 아니오 | 8192 | 1 이상. **장치가 보고한 최대치로 자동 하향 조정** |
| `nguid` | 아니오 | 0 × 32 | **정확히 32자 hex**. 아니면 실패 |
| `query_mem_mode` | 아니오 | `assume_success` | `assume_success` \| `actual`. 오타는 생성 실패 |
| `ignore_read_not_found` | 아니오 | `false` | 문자열 `"true"` / `"false"` 만 허용 |

다섯 개 모두 **백엔드 생성 파라미터**다 — `createBackend()` 를 부르는 쪽(추론 프레임워크)이
정하며, **DOCA_MEMOS 에만 적용된다.** 같은 agent 에 붙은 다른 백엔드는 영향을 받지 않는다.

> agent 설정인 `enable_prog_thread` / `pthrDelay` 와 다른 점이다. 그 둘은 agent 단위라
> **DOCA_MEMOS 만 따로 고를 수 없다** (2.9-2).

기본값의 출처는 두 곳이다:

| 대상 | 위치 |
|---|---|
| 플러그인 파라미터 5개 | `doca_memos_backend.h` 의 멤버 초기값 (`parseInitParams` 는 키가 있을 때만 덮어씀) |
| `useProgThread` / `pthrDelay` | `src/api/cpp/nixl_params.h` 의 `kDefault*` 상수 |

**`num_tasks` 는 호스트 메모리를 잡는다.** `set_num_tasks()` 시점에 그 개수만큼 task 가
한꺼번에 확보된다. task 하나의 크기는 비공개(불투명 핸들)라 총량은 계산할 수 없으나
**값을 키우면 그만큼 늘어난다는 관계는 확실하다.**
같은 이유로 **`DOCA_ERROR_FULL` 은 장치가 바쁜 것이 아니라 task 가 소진된 것**이며,
발생 빈도는 장치 성능이 아니라 이 설정값에 좌우된다.

**`query_mem_mode` 와 `ignore_read_not_found` 는 함께 결정해야 한다.**
기본 조합(`assume_success` + `false`)이 GTC 요구와 정합한다 — 사전 확인 왕복은 생략하되
miss 는 전송 실패로 보고된다. `ignore_read_not_found=true` 는 그 보고를 없애므로
**miss 감지가 필요한 운영 환경에서는 켜지 않아야 한다** (2.6).

### 3.2 런타임 제약

| 항목 | 제약 |
|---|---|
| key 길이 | **≤ 16바이트**. 장치가 더 큰 값을 보고하면 초기화 실패 |
| value 길이 | **≤ 볼륨의 max value 길이**, 그리고 **≤ UINT32_MAX** |
| local memory type | **반드시 `DRAM_SEG`** (VRAM 불가) |
| remote memory type | **반드시 `OBJ_SEG`** |
| **value 버퍼 형태** | **연속 버퍼 1개.** scatter-gather 불가 (iovcnt 고정 1) |
| descriptor 개수 | local과 remote가 **정확히 일치**해야 함 |
| 전송 방향 | `NIXL_READ`(=RETRIEVE) / `NIXL_WRITE`(=STORE) 만 |

### 3.3 환경 요구사항

| 항목 | 값 | 비고 |
|---|---|---|
| DOCA SDK | **4.4 이상** | 공개 문서는 3.4.0까지 → **현재 빌드 불가** |
| 하드웨어 | 플러그인 README: BF-3 이상 / CMX 공식 자료: **BF-4** | **불일치. 4장 참조** |
| 빌드 의존성 | `doca-kv`, `doca-common` pkg-config | 없으면 **경고 없이 조용히 스킵**됨 |
| 프레임워크 | key ≤128비트, huge page, exist 생략, miss 정상처리, context hole, 라우팅 수정 | GTC 요구사항 |

## 4. 확인되지 않은 사항

보고의 정확성을 위해, 차이는 확실하나 근거를 확정할 수 없는 항목을 분리해 둔다.

| 항목 | 상태 | 가능한 근거 후보 |
|---|---|---|
| **GPU 직행 미지원 이유** | 사실 확인, 근거 불명 | 초기 범위 축소 / API 미지원 / KV 경로에서 GPUDirect 미성립 |
| **`nguid`의 역할** | 경로가 이미 namespace를 지목하는데 중복 설정 | ① 경로 불안정성에 대한 **검증**용 ② KV **볼륨 선택자** ③ 단순 전달 |
| **`libdoca_kv`의 커널 인터페이스** | 확인 불가(비공개) | ioctl passthrough / io_uring passthrough |
| **BF-3 vs BF-4** | 문서 간 불일치 | README가 낡았거나, 플러그인 자체는 BF-3에서도 동작 |
| **미사용 API 옵션** | 목 레이어가 `set_do_not_overwrite` / `set_must_exist` 존재를 드러내나 플러그인이 쓰지 않음 | 조건부 쓰기 기능이 있으나 KV 캐시 용도에 불필요 |
| **SGL 미사용** | API가 `iovcnt`를 받는데 `1` 고정 (2.9-1) | 범위 축소 / 볼륨이 고정 슬롯 구조 / 장치측 실제 제약 |
| **스토리지인데 progress 모드 이중 구현** | 사실 확인, 설계 의도만 문서화됨 (2.9-2) | 높은 IOPS 상정 / 저자 배경 / 커스텀 런타임 대비 |

`nguid` 항목의 정황 세 가지: 기본값이 전부 0이면서도 항상 설정 호출이 이루어지고,
지정하지 않으면 경고가 출력되며, **IO 경로에는 전혀 관여하지 않는다** — `doca_kvdev_start()`
직전에 한 번 설정되고 그 뒤로 코드에 등장하지 않으며 progress engine 에 전달되지도 않는다.
셋 다 **필수 선택자가 아니라 선택적 검증 수단**이라는 해석과 정합적이다.
장치 노드 이름이 재부팅 시 바뀔 수 있다는 점(2.10)을 고려하면 **경로가 의도한 장치를
가리키는지 확인하는 수단**으로 보이나, `doca_kvdev_set_nguid()` 의 구현이 비공개라
불일치 시 `start()` 가 실패하는지는 확인할 수 없다.

추가로 확인되지 않은 항목:

| 항목 | 상태 |
|---|---|
| `doca_task_submit()` 이 doorbell 까지 치는가, 폴링 때 몰아 치는가 | 미확인. 목은 후자로 모델링 |
| `libdoca_kv` 가 커널을 통과하는 방식 (ioctl / io_uring passthrough) | 미확인. 성능 특성이 달라진다 |
| 값 버퍼의 핀 고정을 누가 하는가 | 미확인. `registerMem()` 이 아무것도 하지 않으므로 아래 계층 |
| 실제 API 가 key 를 복사하는가, 주소만 잡는가 | 목은 복사. 실제는 미확인 |

## 5. 도입 시 예상되는 관문

우선순위 순으로 정리한다.

**① 프레임워크 수정 (최대 작업량, 플러그인 밖)**
retrieve 실패 정상처리와 context hole 계산은 vLLM/Dynamo의 KV 캐시 매니저 수정을 요구한다.
발표 기준 진행 중이며, 이 작업 없이는 CMX의 이점(부분 재계산)을 얻지 못한다.

**② 현재 빌드·검증 불가**
DOCA 4.4가 미공개다. **유닛 테스트 44개도 돌릴 수 없다** — 목 레이어가 DOCA Core만 스텁하고
`doca_kvdev.h`는 실제 SDK를 요구하기 때문이다. 얼리액세스 확보 전까지는 정적 분석만 가능하다.

> 완화책: 목이 요구하는 심볼(약 72개 함수)로 `doca_kvdev.h` 스텁을 자체 작성하면
> 하드웨어 없이 테스트 실행이 가능해진다. 목 레이어가 사실상 유일한 API 명세 역할을 한다.

**③ 하드웨어 요구가 양쪽이다**
컴퓨트 노드 BlueField와 CMX 박스 BlueField가 **둘 다** 필요하다. 발표 Q&A에서 명시적으로 확인됐다.
컴퓨트측만으로는 동작하지 않는다.

**④ 성능 데이터 부재**
TPS 5배, hit rate 99.8%, goodput 96%는 **전부 시뮬레이션 수치**다. 발표자가
*"실측 성능 데이터는 아직 없다, POC 진행 중"* 이라고 직접 밝혔다.

**⑤ 코드 수준 관찰 사항**
- 소멸자는 in-flight task 를 **최대 10초**까지 drain 하고, 그 안에 끝나지 않은 요청은
  **경고 후 의도적으로 누수**시킨다(UAF 회피). 무스레드형·스레드형 모두 같은 상수를 쓴다
- 배치 전송은 fail-fast — 첫 에러에서 제출을 멈추고 배치 전체를 실패 처리한다.
  이유는 **NIXL에 per-task 상태 보고 API가 없어 부분 성공을 표현할 수 없기 때문**이다.
  이미 제출된 task 는 취소되지 않고 그대로 처리되며 결과만 버려진다.
  같은 API 부재가 **miss 한 descriptor 를 식별할 수 없게 만든다** (2.6-1)
- **키 부재와 장치 오류를 모두 `NIXL_ERR_BACKEND` 로 보고한다.** NIXL 에 이미 있는
  `NIXL_ERR_NOT_FOUND` 를 쓰지 않는다 — API 변경 없이 개선 가능한 지점
- 짧게 읽힌 값(`result_value_len` < 요청 길이)은 **경고 로그만 남기고 성공으로 처리**된다.
  상위로 올라가지 않으므로 프레임워크가 실제 수신 길이를 알 방법이 없다
- 저자가 작성한 실패 모드 분석 문서가 미커버 영역을 스스로 표시해 두었다(초기화 경로의
  일부 DOCA 에러 코드 등)

**⑥ 설정 조합을 명시적으로 결정해야 한다**
기본값을 그대로 쓰면 동작이 GTC 권고와 정합하지만, 다음 셋은 배포 전에 정해야 한다.

| 결정할 것 | 이유 |
|---|---|
| `ignore_read_not_found` 를 켤 것인가 | 켜면 miss 감지 불가 → 재계산 판단 불가 (2.6) |
| progress thread 를 쓸 것인가, 쓴다면 `pthrDelay` 는 | 폴링 의무 유무와 CPU 코어 1개가 걸린다 (2.9-2) |
| KV 블록당 전송 요청을 나눌 것인가 | 나누지 않으면 부분 재계산 불가 (2.6-1) |

## 6. 판단

**플러그인 자체는 도입 난이도가 낮다.** SB API 26개 중 실질 6개만 구현하는 표준적인
스토리지 백엔드이며, NIXL 코어 변경은 3줄에 불과하다. 코드 품질도 높다.

**난이도는 위아래에 있다.**

```
위(프레임워크)  retrieve 실패 처리, context hole, 라우팅, huge page, 128비트 key
                → 코드 수정 필요. 최대 작업량
────────────────────────────────────────────────
      PR #1717   ← 얇음. 실질 6개 함수
────────────────────────────────────────────────
아래(비공개)    DOCA 4.4, DPU 에뮬레이션 구성, CMX 볼륨 생성, BF-4 하드웨어
                → 전부 NVIDIA 의존. 자체 진행 불가
```

**권고**: 현 시점 자체 진행 가능한 작업은 세 가지다.

(a) 목 레이어 기반 스텁 작성으로 테스트 실행 환경 확보
(b) 프레임워크측 요구사항 7가지에 대한 자사 스택 영향도 분석
(c) **전송 단위 설계 결정** — 배치로 묶을 것인가 KV 블록당 요청을 나눌 것인가.
    하드웨어 없이도 판단 가능하며, miss 처리 방식이 여기서 갈린다 (2.6-1)

나머지는 DOCA 4.4 공개 및 하드웨어 확보 이후로 미룰 수밖에 없다.

**NVIDIA 에 확인할 항목** (스펙·문서로 풀리지 않는 것):
GPU 직행 미지원 이유, SGL 미사용 이유, `nguid` 의 실제 역할,
`doca_task_submit()` 의 doorbell 시점, `libdoca_kv` 의 커널 인터페이스.
